# Poker MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a globally deployable, guest-accessible real-time Planning Poker MVP with isolated rooms, up to 100 online members per room, Fibonacci cards, host/voter/observer roles, recent round history, and the Velvet Table visual system.

**Architecture:** A React + Vite + TypeScript single-page application is deployed to Cloudflare Pages. Supabase anonymous authentication, Postgres, RLS, RPC functions, and Realtime provide anonymous-but-authorized room membership, server-authoritative round transitions, and room synchronization. The browser subscribes only to the active room and reconciles a server snapshot after reconnecting.

**Tech Stack:** React, Vite, TypeScript, Supabase JS, Supabase Postgres/RLS/Realtime, Vitest, React Testing Library, Playwright, CSS, Web Crypto API.

**Spec:** `docs/superpowers/specs/2026-09-24-poker-planning-design.md`

## Global Constraints

- The app must support multiple isolated rooms and a maximum of 100 online members per room.
- The user experience must not require registration, OAuth, or a visible account.
- The only card deck in the MVP is Fibonacci: `0, ½, 1, 2, 3, 5, 8, 13, 21, 34, 55, ∞, ?`.
- A room has exactly one host at a time, plus voters and observers; observers cannot vote.
- Votes remain hidden until the host reveals them; results show distribution and the host-entered final estimate, never average or median.
- The round state machine is `voting -> revealed -> archived`.
- The room stores the most recent 20 archived rounds.
- State-changing operations must be server-authoritative, role-checked, state-checked, and idempotent where repeated clicks are possible.
- The visual direction is Velvet Table: dark felt, warm card stock, gold accents, stacked cards, restrained motion, and no copied game assets.
- Animations must use `transform` and `opacity` where possible and respect `prefers-reduced-motion`.
- `.superpowers/` is temporary design-preview output and must remain ignored by Git.
- Free-tier deployment limits must be documented; the implementation must not claim SLA-level availability.

## Review Focus

- A vote submitted during a stale `voting` snapshot must either be accepted once by the server or produce an explicit conflict without changing local success state; covered by the vote RPC integration test and client reconciliation test.
- A non-host, observer, or member from another room must not be able to reveal, archive, transfer host, or read hidden votes; covered by RLS/RPC permission tests.
- A room at 100 online members must reject the next join without creating a partial member row; covered by the join transaction test.
- A reconnect during or immediately after Reveal must fetch the authoritative snapshot and show revealed cards rather than stale backs; covered by the realtime reconnect test.
- Reduced-motion users must receive the same usable state changes without flip, float, or growing-bar animation; covered by the accessibility browser test.
